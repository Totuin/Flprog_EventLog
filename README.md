# Flprog_EventLog 1.0.1 — журнал событий FLProg

## Назначение

`FlprogEventLog` хранит события в оперативной памяти, `FlprogEepromEventLog` — через библиотеку `Flprog_EEPROM` и её RAM-копию. Типы полей задаются через `setTimeField`, `setByteField`, `setIntegerField`, `setBooleanField`, `setLongField`, `setUnLongField` **до** записи событий. Публичный интерфейс предыдущей версии сохранён, включая написание `setEEprom()` и `FlprogEventLogUnLongteValueField`.

События в журнале упорядочены от новых к старым: логический индекс **0** — самое новое. `addNewEvent(id)` добавляет событие и возвращает указатель на запись либо `nullptr` при неверном id. Когда журнал заполнен, новая запись вытесняет старейшую. `hasEvent`, `event`, `get*Value` используют логический индекс. `resetRecord` и `clearEventLog` освобождают слоты, сбрасывая веса.

ID события хранится **одним байтом** (0..255); конструктор допускает больше типов по исторической сигнатуре, но `addNewEvent` отвергает ID >255, чтобы не допустить усечения. Сохранённая запись содержит 1 байт ID и 2 байта веса. Описания типов в EEPROM не записываются.

## EEPROM: порядок и формат

1. Создать `FLProgInternalEEPROM` или `FLProgExternalEEPROM` с достаточным размером.
2. Создать `FlprogEepromEventLog(eventsSize, recordsSize, fieldsSize)`.
3. **Задать тип каждого поля** методами `set*Field()`; неполную схему лучше не использовать.
4. Вызвать `uint16_t next = log.setEEprom(&eeprom, startAddress)` (стартовый адрес **>= 1**, потому что байт 0 зарезервирован под маркер EEPROM).
5. Проверить `next != 0` и `next <= configuredEepromSize`. Если возвращён 0 — разметка не выполнена.
6. Вызвать `eeprom.begin()` и регулярно вызывать `eeprom.pool()` в `loop()` для физической записи данных. **Не** писать события на каждом обороте цикла.

Разметка остаётся совместимой с 1.0.0: сначала все bool-поля всех записей, упакованные в биты; затем для каждой записи 1 байт ID, 2 байта веса, потом все небулевы поля в заданном порядке. Размеры: byte — 1, int16 — 2, long/unsigned long/time — 4 байта. Порядок байтов определяется `Flprog_EEPROM` и не изменялся. Версия 1.0.1 **не обнуляет веса при привязке**, поэтому сохранённая история остаётся доступной после повторного запуска.

**Ограничения:** метод `setEEprom` не знает физическую ёмкость чипа; он проверяет только переполнение 16-битного адреса и должен проверяться вызывающим кодом на фактический размер EEPROM. Маркер инициализации и начальные значения зависят от `Flprog_EEPROM`. При неожиданном обесточивании во время нескольких отложенных записей целостность всей транзакции не гарантируется. После изменения схемы типов полей сохранённый формат будет несовместим: нужна отдельная миграция или очистка данных.

## Память и производительность

В RAM-журнале память полей и записей выделяется динамически. Объекты имеют владеющие деструкторы и не копируются. На микроконтроллерах с небольшим объёмом RAM задавайте разумное число записей. Алгоритм сортировки по весам — O(N²), рассчитан на короткие журналы; при частом опросе больших журналов стоит оценить задержку. Возврат из `get*Value` для несуществующего поля — ноль/false.

Поле, не заполненное после повторного использования слота, может содержать старые данные. **Всегда заполняйте все используемые поля после `addNewEvent()`**. В RAM все новые поля инициализируются нулём, но повторно используемая запись сохраняет значения до перезаписи. В EEPROM поля не очищаются автоматически для уменьшения числа циклов записи.

## Проверка

`examples/basicEventLog` — RAM; `examples/eepromEventLog` — EEPROM. В `tests/` лежит автономный C++11 тест с имитацией EEPROM: он не заменяет проверку на аппаратной платформе и реальной EEPROM.
